# Phase 1 · Step 4 — Roadmap

## Overview

- **Purpose**: Prioritise features into Must / Should / Could / Won't, set the dependency-aware build order, and choose the Phase 2 scope.
- **Agent/Skill**: general-purpose agent drafts; the human makes every priority, cut/keep, and scope call.
- **Model**: `balanced`
- **Trigger**: Step 3 gate approved.
- **Inputs**: `docs/idea-brief.md`; `docs/market-notes.md` *(if Step 2 ran)*; `docs/prototype/`; `docs/DESIGN.md`.
- **Outputs**: `docs/roadmap.md` — build order, deferred features, `Phase 2 Scope`; `docs/backlog.json` — feature list; `docs/backlog.html` — rendered board.
- **Template**: `templates/04-roadmap.md`, `templates/backlog.json`
- **Gate**: `hard` — product-scope decision.

## Scope

- **In**: MoSCoW prioritisation; evaluating each market-research feature inspiration; build order; explicit deferrals; the Phase 2 scope recommendation.
- **Out**: technical decisions (Step 6); sprint or milestone assignment; applying the scope recommendation without human confirmation.

## Execution Rules

- **Feature inspirations**: for each entry in `docs/market-notes.md` Section 5, place it in a MoSCoW tier or mark it `Won't (out of scope)` with a one-line reason. None may be silently ignored. If Step 2 was skipped, say so in the roadmap and flag assumptions made about priorities.
- All features (original and inspirations) are written to `docs/backlog.json` under one release entry (`id` `r1`, `name`, `status: planned`). Each feature is `pending` with `release` set to that id and a `created` event (`at` as an ISO date-time, `source: live`, `by: orchestrator`, `note`). Won't features and any deferred feature get `release: null`, status `deferred`, and a `deferred` event. The roadmap table is generated by `node kit/scripts/render-backlog.js`; Phase 2 appends events as features start and ship.
- **Build order** follows dependencies, not only tier: a lower-priority feature that a Must feature depends on comes first.
- **Deferred** features are listed in the Explicitly Deferred section, never dropped.
- **Phase 2 Scope** (`all` | `feature`) — the single selection rule for the kit, evaluated on the Must features once the draft is ready, before presenting it:

  | Criterion | `scope: all` (whole app in one cycle) | `scope: feature` (one feature per cycle) |
  |---|---|---|
  | Must feature count | ≤ 15 | > 15 |
  | Feature sizes | All S or M | Any L |
  | Domains | One primary domain; any other domain is < 20% of Must features | A second domain is ≥ 20% of Must features |
  | Dependency structure | Tight chain, each feature builds on the previous | Independent parallel streams |
  | Developers | Solo | Team |

  **Domain** means a distinct area of work that needs a different specialist skill, or a separate deployable concern. A typical web app with UI and API is **one** domain (frontend/backend is not a domain split). A web app plus a mobile app plus an ML pipeline is three. Expected result for a typical full-stack MVP: one domain, so `scope: all`.

  Recommend `all` only if all five criteria point to it; **any one criterion pointing to `feature` overrides the rest.** Write the recommendation, the five criterion scores, and a one-line rationale in the roadmap's `Phase 2 Scope` section. The human confirms; it is never applied automatically.

  **Mid-cycle escape:** if Phase 2 Plan (`kit/steps/phase-2/p2-02-plan.md`) finds, counting domains by the definition above, that a second domain holds ≥ 20% of the tasks under `scope: all`, it recommends switching to `scope: feature` (experimental) and asks the user. On user confirmation, update the `Phase 2 Scope` field in `docs/roadmap.md` and `phase2_scope` in `docs/backlog.json`.

- **Admin Site** (`yes` | `no` | `later`): ask once, before presenting the draft: "Will this product need an administrator site (to manage users, content, payments, and so on)?" Record the answer in the roadmap metadata. It is a hint for `kit/phase-admin.md`, which runs after Phase 2. It is **never a feature row** and is **excluded from every Phase 2 Scope criterion**: counting it would inflate the Must count or the domain split and could flip the scope to `feature`. `no` and `later` need no further work in Phase 1.
- **Source references** (`requirements` mode, `docs/idea-brief.md` has `Provenance: requirements`): a feature derived from a requirement records its source at the start of its `description` in `docs/backlog.json` as `[Src: BRD §3.2]`, copied from the brief's `Source Trace`. A feature that needs no `description` otherwise gets one containing only the tag. The `backlog.json` schema is unchanged. A feature with no source requirement (added by the team or from market research) carries no tag.
- **Non-functional requirements** (`## 7. Non-functional Requirements` in the template): ask once, in one combined round, never item by item, before presenting the draft. Offer defaults by project type and let the user answer "defaults", edit rows, or mark a category `n/a — <reason>`. Categories: security and privacy, performance, accessibility, i18n/l10n, availability and observability, compliance. Defaults: *web app with accounts* — security (authentication on every non-public route, no secrets in the repo, input validation), performance (main page interactive under 3 s on a mid-range device), accessibility (WCAG 2.1 AA, no critical violations in an automated scan), observability (errors logged); *API or backend service* — security, performance (p95 latency target), availability and observability (health endpoint, structured logs); *CLI or library* — mostly `n/a`; *internal tool* — accessibility and i18n `n/a`. Each row needs a measurable target, or the cell says `n/a — <reason>`. Fill the table (it may be all `n/a`), and set `Applies to` and `Verified by` (Review, an E2E case, or a Verification Commands row). Step 7 maps each row with a measurable target to a constitution MUST or Verification Commands row.

## Artifact Rules

- Write `docs/backlog.json` from `templates/backlog.json`. Fill `project` (the project name), `phase2_scope`, and `admin_site` with the same values as the roadmap metadata; the validator rejects empty values. Whenever `Phase 2 Scope` or `Admin Site` changes later, update both places. Then run `node kit/scripts/render-backlog.js`; never hand-edit the generated table or `docs/backlog.html`. Write the rest of `docs/roadmap.md` from the template.
- Keep the template's metadata block and section numbering (Phase 3 appends release blocks and reads Section 4).
- Set `Status: approved` when the human confirms scope and Phase 2 Scope at the gate.

## Completion Criteria

- [ ] All features listed and MoSCoW-prioritised; every Must feature traces to the Core User Flow; no tech-stack assumptions in feature descriptions.
- [ ] Build order reflects the dependency chain; deferred features captured.
- [ ] `docs/backlog.json` validates and the render script exits 0.
- [ ] `Phase 2 Scope` written with criterion scores.
- [ ] `Admin Site` answered and recorded in the roadmap metadata; no admin feature row added.
- [ ] `requirements` mode: every Must feature derived from a requirement has `[Src: ...]` at the start of its `description`.
- [ ] Human confirmed the feature scope and `Phase 2 Scope`.
- [ ] The `Non-functional Requirements` table is filled from one combined question (all `n/a` is valid); every row has a measurable target or `n/a — <reason>`.

Gate summary: *"The feature roadmap is set: [N] Must features in build order, [X] items explicitly deferred, Phase 2 will run as scope [all|feature]. Does this scope match what you want to ship for the MVP?"*
